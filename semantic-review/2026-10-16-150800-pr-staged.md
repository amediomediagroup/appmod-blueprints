# Azure Bootstrap Infrastructure with AVM Module

This change adds Azure bootstrap infrastructure using the Azure Verified Module (AVM) pattern for GitHub CI/CD, enabling the kind-crossplane-azure cluster provider. The implementation creates a one-time init script for initial authentication setup, then uses Terraform with the AVM module to provision a GitHub environment with OIDC federated credentials, a bootstrap Key Vault for storing all platform configuration (zero PII in committed code), and the hub resource group where Crossplane will later provision AKS. The bootstrap flow uses a privilege separation model: an initial "init" UAMI with Owner rights creates the infrastructure, then a platform UAMI with Contributor rights handles ongoing operations.

**Watch for:** Duplicate `principal_id` assignment in `azurerm_role_assignment.uami_hub_contributor` causing Terraform validation failure; Owner role on subscription-wide scope for init UAMI creates broad blast radius if the GitHub repo is compromised; federated credential subject matches only `main` branch not the bootstrap environment.

**Verdict:** NEEDS_CHANGES

## High-level view

The AVM module creates User-Assigned Managed Identities with federated credentials tied to the GitHub environment, eliminating client secrets in favor of OIDC token exchange. The module is pinned to v0.1.1 for reproducibility.

The init.sh script grants Owner at subscription scope to the init UAMI, necessary for the AVM module to create role assignments but creating significant blast radius during the bootstrap window. The script writes backend.conf locally (gitignored) and sets GitHub secrets via `gh secret set`.

The GitHub Actions workflow uses the init UAMI for Terraform operations and passes sensitive values through TF_VAR_* environment variables. Environment secrets created by Terraform (AZURE_CLIENT_ID, AZURE_TENANT_ID, BOOTSTRAP_KV_NAME) are set in the `azure-hub` environment, distinct from the `bootstrap` environment used for the workflow itself.

The Key Vault stores platform configuration as a single JSON secret with `ignore_changes` lifecycle to preserve post-install modifications. RBAC authorization is enabled with the platform UAMI granted Key Vault Secrets User role for runtime reads.

<summary>Issues (3)</summary>

1. **Duplicate principal_id assignment** — The `azurerm_role_assignment.uami_hub_contributor` resource defines `principal_id` twice (lines 68-73): once with a conditional returning `null` and again on line 76. Terraform will fail validation with "duplicate argument" error. Remove the conditional block and keep only the data source reference.

2. **Subscription-wide Owner for init UAMI** — init.sh grants Owner role at subscription scope to the bootstrap UAMI, giving full control over all resources in the subscription during the bootstrap window. If the GitHub repo is compromised before the role is revoked, an attacker could use the federated credential to modify or delete any Azure resource. Consider scoping to a specific resource group or documenting the revocation step as mandatory (not optional).

3. **Federated credential subject mismatch** — The federated credential created by init.sh uses subject `repo:${GITHUB_ORG}/${GITHUB_REPO}:ref:refs/heads/main` which matches any workflow run on the main branch. The workflow runs in the `bootstrap` environment, but the subject does not include `environment:bootstrap`. A malicious actor with write access to main could trigger the workflow and obtain an OIDC token valid for the init UAMI. Consider using `repo:${GITHUB_ORG}/${GITHUB_REPO}:environment:bootstrap` to restrict to the environment.

## Terraform validation error in role assignment

The `azurerm_role_assignment.uami_hub_contributor` resource has a syntax error that will prevent Terraform from validating:

```
resource "azurerm_role_assignment" "uami_hub_contributor" {
  ...
  principal_id = module.cicd_bootstrap.managed_identity_client_ids[var.github_environment] != null ? (
    null # resolved via data source below
  ) : null

  # Resolved via data source
  principal_id = data.azurerm_user_assigned_identity.platform_write.principal_id
}
```

Terraform does not allow duplicate argument names in a resource block. The conditional returning `null` appears to be a remnant of an earlier approach. The fix is to remove lines 68-73 and keep only the data source reference:

```
resource "azurerm_role_assignment" "uami_hub_contributor" {
  scope                = azurerm_resource_group.hub.id
  role_definition_name = "Contributor"
  principal_id         = data.azurerm_user_assigned_identity.platform_write.principal_id
}
```

## Init script security model

The init.sh script implements a bootstrap identity pattern with privilege escalation:

1. User runs `az login` locally with Contributor + User Access Administrator
2. Script creates init UAMI with Owner at subscription scope
3. Script creates federated credential tied to main branch
4. Script sets 3 GitHub secrets (CLIENT_ID, TENANT_ID, SUBSCRIPTION_ID)
5. GitHub Actions workflow authenticates as init UAMI via OIDC
6. Terraform creates AVM infrastructure including platform UAMI
7. After bootstrap, Owner role can be revoked from init UAMI

During steps 2-5, any workflow run on main can authenticate as the init UAMI with Owner rights on the entire subscription. The script notes revocation as "optional" but should document it as strongly recommended, or the federated credential subject should be scoped to the bootstrap environment.

The script correctly masks sensitive values in output and uses `set -euo pipefail` for error handling. The random suffix for storage account name ensures uniqueness.

## AVM module and identity topology

The data source `azurerm_user_assigned_identity.platform_write` looks up the UAMI created by AVM by constructing the expected name pattern. This relies on AVM's naming convention, which could break if the module changes, but pinning to v0.1.1 mitigates this risk.

The GitHub provider uses `GITHUB_TOKEN` environment variable for authentication — the default Actions token with repository scope, sufficient for creating environment secrets.

## GitHub Actions workflow

The workflow uses `workflow_dispatch` for manual triggers with plan/apply/destroy actions, plus automatic triggers on push to main. The `environment: bootstrap` creates an optional environment that can have protection rules but is not enforced by default.

Sensitive variables pass via `TF_VAR_*` environment variables from GitHub secrets; non-sensitive values from repository variables. The backend config passes via file (`backend.conf`) with secrets via command-line arguments.

## Key Vault and secrets management

The bootstrap Key Vault uses RBAC authorization with Standard SKU, soft delete with 7-day retention, and purge protection disabled — acceptable for bootstrap configuration storage.

The `platform-config` secret stores all platform configuration as JSON with `lifecycle { ignore_changes = [value] }` to preserve post-install modifications like `overlay_repo_url`.

Role assignments grant Key Vault Secrets Officer to the Terraform runner (for seeding) and Key Vault Secrets User to the platform UAMI (for runtime reads).

## No PII in committed files

The `terraform.tfvars.example` file contains only placeholders with clear instructions that sensitive values must be passed via environment variables in CI. The `.gitignore` additions cover `terraform.tfvars`, `backend.conf`, `.terraform/`, and `tfplan`. No account IDs, tenant IDs, or client IDs appear in the committed diff.
